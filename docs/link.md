# umcub link

Several devices on one bus: addressing, the SECURE mode (authentication, encryption) and the host tool.

## Addressing

SMP over a serial line is point to point: on a shared RS485 bus every bootloader would answer at once, and anybody
on the bus could drive them. The umcub link puts an envelope around SMP and text commands, per transport:

| `UMCUB_CFG_<UART\|USB_CDC\|CAN\|ETH\|USER>_LINK_...` | What the transport accepts |
|---|---|
| `_PLAIN` (default) | SMP and text as before; standard `mcumgr` / `smpmgr` |
| `_ADDRESSED` | only umcub link frames: a device answers frames for its node address (or, unassigned, for its UID after a `HELLO` with that UID), discovery with random back-off |
| `_SECURE` | addressed, and nothing is executed before the host has authenticated; every frame of the session carries a MAC |

CAN has `_PLAIN` and `_SECURE` only: a node's CAN IDs (bases + node address) already select it. A SECURE CAN node
runs the link over its own IDs and needs a node address other than 0; `discover` on CAN finds it by a HELLO (its
identity, nothing executed), and `--node N` with the keys opens the session. A UID selects nobody on CAN: unassigned
nodes share the base IDs. The host side needs the host library 0.6.0 or later (older ones refuse the keys on CAN and
do not find a SECURE CAN node); SECURE on any transport wants 0.6.3 or later (the failed-handshake fixes below).

Frames: magic, version, type, flags, destination, source, sequence number, length, payload, optional 16-byte tag.
Packet transports (CAN ISO-TP, UDP, board packet transports) carry them as they are, stream transports (UART, USB
CDC) as a line `0x05 0x0B <base64> \n` (0x05 always starts a line: one cut short by a collision costs only itself).
The format and the handshake are described in [`src/proto/include/umcub_link.h`](../src/proto/include/umcub_link.h).
RS485 needs the driver-enable pin (`UMCUB_CFG_UART_DE_*`; hardware DE on the H7, software on the F1 and F4) and no
log on that UART. A 5 V transceiver (MAX485 and alike) does not drive the bus properly from 3.3 V: power it from 5 V
and put its RO output on a 5 V-tolerant RX pin, or use a 3.3 V part (MAX3485, SP3485).

## SECURE mode

The host answers a fresh 32-byte challenge with an ephemeral EC P-256 key, its own nonce and an ECDSA signature made
with the **admin key**. The bootloader checks the signature with the embedded public half, derives the session keys
from ECDH with its **device key** (HKDF-SHA256) and proves in `AUTH_OK` that it holds that key. After that every frame
has an HMAC-SHA256 tag (16 bytes) and a strictly increasing sequence number, so a recorded frame or `AUTH` cannot be
replayed and a frame cannot be changed. `UMCUB_CFG_LINK_ENCRYPT` also encrypts the payloads (AES-128-CTR), so a
sniffer does not see the firmware either. A SECURE device's `ANNOUNCE` and `CHALLENGE` carry its UID, node address and
board type, but not the board revision and the bootloader version (zeros): nobody on the bus learns which node runs an
old bootloader. The host reads them inside the session (`discover` shows them as `hidden`, `info` has them; host
library 0.6.7 or later, older ones show `0.0.0`). A session belongs to one host on one transport and ends with `CLOSE`
or after `UMCUB_CFG_LINK_SESSION_MS` (20 s .. 1 h) without a valid frame; the host library sends HELLO again after
20 s without a request. With the keys given it never sends or takes DATA outside a SECURE session: after a failed
handshake the next request runs the handshake again (and raises its error; a bare `Link` raises `link.no_session`),
and a device with another UID at the same address is refused (`link.other_device`; a shared product key would let a
swapped controller authenticate). A failed `AUTH` blocks the next one for a second.

Keys are files, like the signing key: generated by the first configure, or your own (menu *Keys*,
[Kconfig](configuration.md#kconfig)):

```
keys/<board>/device.pem     # stays in the bootloader (private)
keys/<board>/admin.pem      # stays on the hosts allowed to update
```

CMake embeds them with `umcub keys` (`c`: device private key and admin public key for the bootloader;
`host-c`: the host side for C tools and tests); the device key for [encrypted images](security.md#encrypted-images) with
`imgtool getpriv`. `tools/keys/dev-device-p256.pem` and `dev-admin-p256.pem` are
development keys from the repository, the build warns about them.

### Limits

- The device key is the same in every device of a product. With flash readout protection off it can be read out
  with a debugger, so a SECURE transport stays closed (`HELLO` gets an `ANNOUNCE` flagged closed) while RDP is at
  level 0, unless `UMCUB_CFG_LINK_REQUIRE_RDP` is 0 (development only).
- USB DFU cannot authenticate the host: together with a SECURE transport it is refused at build time unless
  `UMCUB_CFG_USB_DFU_ALLOW_UNAUTH` is set.
- The F1 and the F411 have no true RNG: nonces come from the noise of the low ADC bits (internal temperature
  sensor; measured per 32-byte block at room temperature with `tests/hw/entropy_test.py`: 60-80 bits of
  min-entropy on a Blue Pill, about 99 bits on a Black Pill F411),
  hashed with the UID, a boot counter kept in RAM over resets and (SECURE) keyed with the device key. That is
  plenty for challenges that must not repeat; a colder or quieter part has less noise, so measure a new board. Randomness is fail-closed: if the entropy source fails
  or its output looks stuck, `HELLO` gets no challenge.
- A failed `AUTH` blocks further attempts for one second, a challenge is valid for ten seconds. An `AUTH` costs two
  ECC operations (about 1.3 s on a 72 MHz Cortex-M3), so with SECURE `UMCUB_CFG_WATCHDOG_MS` (if set) must be at least 2000
  and, with SMP, the lite upload or a board protocol, `UMCUB_CFG_VALIDATE_PRIMARY` must stay on (both checked at build
  time).
- The policy is per transport: a PLAIN or ADDRESSED transport next to a SECURE one is a way around it, the build warns unless
  `UMCUB_CFG_LINK_MIXED_OK` is set. A UART with a link never carries the log.
- A bus can always be jammed; the link protects authenticity, integrity, replay and (with encryption)
  confidentiality. Like jamming, another bus member can disturb a login (its HELLO replaces the pending challenge)
  or a session with a node selected by UID (a HELLO for another UID deselects it): the host retries, nobody takes a
  session over.
- Firmware confidentiality needs two things: `UMCUB_CFG_LINK_ENCRYPT` for the session and
  [encrypted images](security.md#encrypted-images) for what is stored and sent outside it.

## Host side: the `umcub` tool

Standard SMP clients do not speak the link. The [`umcub` tool](host.md) finds the devices, selects one, uploads to
it and, as a proxy, serves `mcumgr` / `smpmgr` unchanged.

`discover` broadcasts DISCOVER with a number of slots; every device answers ANNOUNCE in a random slot. Two devices in
one slot collide and the host receives garbage; the next round lists the UIDs found so far (those stay silent) and
the rest draw new slots. Rounds end after a quiet one - nothing new and nothing garbled - or after `--rounds`
(default 8). Fewer `--slots` make discovery faster and collisions more likely. From host library 0.6.5 the host
(and `sniff`, for link frames) also starts a line at a frame start (`05 0B`, `05 0C`, `05 0E`), so a line cut short
by a collision costs only itself there too.

```sh
umcub -d /dev/ttyUSB0 discover                                # all devices on the bus (random back-off rounds)
umcub -d /dev/ttyUSB0 --node 5 info                           # identity; SECURE: authenticates first
umcub -d /dev/ttyUSB0 --uid 53ff7206... cmd i                 # unassigned node, selected by UID
umcub -d /dev/ttyUSB0 --node 5 --admin-key admin.pem --device-key device.pem upload app.encrypted.bin
umcub -d /dev/ttyUSB0 --node 5 --admin-key admin.pem --device-key device.pem serve --pty-link /tmp/smp
smpmgr --port /tmp/smp --line-buffers 4 image upload app.encrypted.bin    # through the proxy
umcub -d 192.168.1.50 --node 5 serve --udp-listen 127.0.0.1:1337   # mcumgr --conntype udp
umcub -d /dev/ttyUSB1 sniff                                   # listen only: every frame on the bus, decoded
```

SECURE transports need `--admin-key` (private) and `--device-key` (the public half is enough). With the keys given
the tool accepts only a SECURE session: a device that answers HELLO without a challenge (another link mode, or a
forged answer on the bus) is refused (`link.not_secure`), so a session cannot be downgraded. Keys where no SECURE
session can be used (CAN without `--node` or with node 0, serial / UDP without `--node` or `--uid`) are an error too
(`link.keys_unused`). `serve` hands the authenticated session to every client of its pseudo terminal or UDP port: with
a SECURE session it listens on loopback addresses only (`serve.secure_remote`); other local processes of the PC can
still use it while it runs.

Your own host software can do the same: the frames and the handshake are in `umcub_link.h`, `tools/host/umcub/link.py`
is a complete reference (Python `cryptography`).
